# 内部技术审计：单片指数退避重试机制 (v1.35.21)

本报告记录了对 `offscreen/main.js` 拉取引擎的增强，旨在从分片（Segment）级别处理瞬态网络故障（如 502, 429 等）。

## 1. 问题背景
在大规模 HLS/DASH 下载（700+ 分片）中，极易遇到瞬时网络波动或服务端过载。
- **旧版 (v1.35.19/20)**：在初始并发池失败后采用“全局重试”轮次。如果 Worker 0 在处理第 10 个分片时遇到 502，它会等到整个并发池结束后才进行重试。
- **痛点**：单个分片的 502 会导致该 Worker 线程提前停止，降低了整体下载效率。

## 2. 技术方案：分片级重试循环

### A. 基于状态码的过滤 (Status Filtering)
我们定义了 `RETRYABLE_STATUSES` 集合，仅针对可恢复的服务器错误进行重试：
- **429**: Too Many Requests（触发限流）。
- **500, 502, 503, 504**: 服务端错误。
对于 **404 (Not Found)** 或 **403 (Forbidden)** 等不可恢复错误，逻辑会直接跳过重试，避免无效的死循环。

### B. 指数退避 (Exponential Backoff)
为每个待重试的分片实现了带等待期的本地循环：
```javascript
const delay = 500 * Math.pow(2, attempt - 1); // 500ms -> 1000ms
```
该策略有效防止了“惊群效应（Thundering Herd）”，即多个 Worker 同时重试导致服务端压力进一步崩溃。

### C. 资源优化
将 `RETRYABLE_STATUSES` 和 `MAX_ATTEMPTS` 常量移出 `fetchAndProcess` 函数，避免在数千次循环中重复创建对象，优化了执行效率。

---

## 3. 错误处理流 (Failure Flow)

1.  **第一层（本地重试）**：Worker 尝试 3 次并伴随指数退避。
2.  **第二层（错误追踪）**：若三轮均失败，索引被推入 `failedSegments`。
3.  **第三层（终极兜底）**：并发池结束后，`Retry Pass` 模块会对幸存的所有失败分片进行最后一轮单线程修补。

## 4. 审计结论
v1.35.21 是目前最强韧的下载引擎版本。它结合了 **原子化索引认领 (v1.35.19)** 与 **颗粒化重试自愈 (v1.35.21)**，能够从容应对各种不稳定的网络环境，具备工业级稳定性。
